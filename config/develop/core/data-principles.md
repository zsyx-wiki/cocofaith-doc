# 迁移与数据原则

Core 管的是长期数据：UID、身份、玩家资产、背包、业务状态和审计流水。这里的改动要比普通玩法更保守。

## 持久标识

发布后不要随意修改：

- `uid`
- `item_id`
- 信仰名和持久化信仰标识
- 职业 ID
- 业务名
- 身份 `adapter/type/scope`
- 数据库表名和字段含义

显示名称可以调整，持久标识不应跟随文案变化。

## 数据迁移

涉及表结构或历史数据含义变化时，应提供迁移脚本。Core 已有脚本目录：

```text
scripts/
```

迁移脚本建议具备：

- 可重复运行或明确拒绝重复运行。
- 执行前检查版本或数据形态。
- 输出影响条数。
- 保留备份建议。
- 失败时尽量不留下半迁移状态。

## 备份要求

生产环境执行迁移前至少备份：

- Koishi 数据库。
- Koishi 配置。
- 三个插件源码提交版本。
- Adapter openid 配置。

## 数据完整性

Core 提供 `integrity` 服务检查或清理：

- 无效背包物品。
- 过期效果。
- 过期权限。
- 玩家基础数据异常。

迁移后应运行完整性检查，再用低风险命令验证，例如 `关于椰子水`、`信仰 信息`。

## 兼容原则

- 能新增字段就不要复用旧字段为新含义。
- 业务私有数据优先放 `faith_core_business` 或业务表，不要塞进玩家公共表。
- Adapter 不拥有数据迁移权。
- Business 不直接改 Core 公共表结构。
